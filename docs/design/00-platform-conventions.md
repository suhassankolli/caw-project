# CollabHub — Platform Conventions

> Shared baseline for all backend services. Every service doc references this file
> instead of repeating cross-cutting rules. Read this first.

**Status:** Draft · **Applies to:** Auth, Messaging, Canvas, Asset, Worker services
**Stack baseline:** Python 3.13+ · FastAPI (ASGI, Uvicorn) · python-socketio · Kubernetes

---

## 1. Purpose

This document defines conventions every CollabHub backend service MUST follow so that
the services are consistent, independently buildable, and portable across on-prem
Kubernetes and (later) Azure. Where a service doc and this doc disagree, **this doc wins**
unless the service doc explicitly overrides a section and says so.

---

## 2. Repository & Project Layout

Mono-repo managed as a **uv workspace**: one root `pyproject.toml`, one package per service,
plus shared libraries that services depend on as workspace members.

```
pyproject.toml                 # uv workspace root (members = libs/*, services/*)
uv.lock                        # single lock file for the whole workspace
/libs
  /collabhub-shared            # Cross-cutting: Problem Details handlers, JWT verifier, telemetry,
                               #   settings base class, job envelope + stream helpers
  /collabhub-contracts         # Pydantic models (DTOs + job payloads) shared across service boundaries
/services
  /auth                        # package collabhub_auth
  /messaging                   # package collabhub_messaging
  /canvas                      # package collabhub_canvas
  /asset                       # package collabhub_asset
  /worker                      # package collabhub_worker
/deploy
  /helm                        # One chart per service + umbrella chart
  /k8s                         # Raw manifests / kustomize overlays (on-prem, azure)
/docs/design                   # These design docs
```

Each service is a separate container image, separately deployable, with its own
Helm chart and its own database migration history (Alembic, per service). Services MUST NOT
share a database schema; cross-service reads go through the owning service's API or through events.

### 2.1 Python runtime baseline

| Concern | Choice |
|---------|--------|
| Language | Python 3.13+, fully type-hinted; `mypy --strict` (or pyright) in CI |
| Packaging | `uv` workspace; images built from `uv.lock` (`uv sync --frozen`) |
| Web framework | FastAPI on Uvicorn (`uvloop`, `httptools`) |
| Real-time | `python-socketio` (ASGI mode) mounted alongside FastAPI — see §6 |
| Validation / DTOs | Pydantic v2 |
| Settings | `pydantic-settings` (env vars, §8) |
| Database | SQLAlchemy 2.0 (async) + `asyncpg`; Alembic migrations |
| Redis | `redis-py` asyncio client (`redis.asyncio`) |
| HTTP client | `httpx` (async) |
| JSON | `orjson` (`ORJSONResponse`) |
| Lint / format | `ruff` |

- **Async everywhere on the request path.** Never call blocking I/O (sync DB drivers,
  `requests`, `time.sleep`) inside an `async def` handler. CPU-heavy work (image processing,
  rendering) belongs in the Worker, in a process pool.
- **One Uvicorn process per pod.** Scale with pod replicas (HPA), not `--workers`, so that
  K8s probes, resource limits and Socket.IO session affinity map 1:1 onto pods.

## 3. Identifiers, Time, and Concurrency

- **IDs:** UUID v7 (time-ordered) for all primary keys. Stored as `uuid` in PostgreSQL.
  Generated by the application, not the database, so IDs are known before insert. Use one
  `new_id()` helper in `collabhub-shared` (stdlib `uuid.uuid7()` where the runtime provides it,
  otherwise the `uuid-utils` package).
- **Timestamps:** Always UTC, stored as `timestamptz`. Serialised as ISO-8601 with `Z`.
  Column names `created_at`, `updated_at`. Never store local time; never use naive
  `datetime` objects (`datetime.now(UTC)` only).
- **Soft delete:** Mutable user-facing resources use `deleted_at timestamptz NULL`.
  Queries filter `deleted_at IS NULL` by default. Hard delete only via retention jobs.
- **Optimistic concurrency:** Updatable rows carry a `version integer NOT NULL DEFAULT 0`,
  incremented on every update. Updates use `WHERE id = :id AND version = :expected_version`
  (SQLAlchemy `version_id_col`, or an explicit `UPDATE ... RETURNING`); zero rows affected →
  `409 Conflict`.

## 4. REST API Conventions

- **Base path:** `/api/v1`. Breaking changes bump the version segment. Mounted at the root
  instead: `/.well-known/*` (JWKS, OIDC discovery), `/health/*`, and real-time paths (`/hubs/*`).
- **Resource naming:** plural nouns, lowercase; multi-word segments use kebab-case
  (`/upload-url`, `/download-url`). Prefer single words where possible (`/documents`, not
  `/canvas-docs`). Sub-resources nest one level max (`/channels/{id}/messages`).
- **JSON field naming:** camelCase on the wire. Pydantic models use snake_case attributes with
  `alias_generator=to_camel` and `populate_by_name=True`, defined once in a base model in
  `collabhub-contracts`. (OAuth token endpoints are the exception: RFC 6749 mandates snake_case.)
- **Verbs:** `GET` (read, safe), `POST` (create / non-idempotent action),
  `PUT` (full replace), `PATCH` (partial update, JSON Merge Patch **RFC 7396**,
  `application/merge-patch+json`), `DELETE`.
- **Content type:** `application/json` request/response unless stated.
- **OpenAPI:** every service exposes its FastAPI-generated schema at `/api/v1/openapi.json`;
  it is the source for generated frontend clients.
- **Auth:** `Authorization: Bearer <access-token>` on every endpoint except health checks,
  `/.well-known/*`, and the Auth service's login/callback/token/refresh endpoints.

### 4.1 Pagination (cursor-based)

List endpoints accept `?limit=` (default 50, max 200) and `?cursor=` (opaque, base64).
Response shape:

```json
{
  "items": [ /* ... */ ],
  "nextCursor": "eyJ0cyI6..."   // null when no more pages
}
```

Cursors encode the sort key of the last returned row (e.g. `(created_at, id)`, or just `id`
where UUID v7 ordering is the sort) and MUST be stable across requests. Never use OFFSET for
user-facing lists. A generic `Page[T]` Pydantic model lives in `collabhub-contracts`.

### 4.2 Error Envelope (RFC 9457 Problem Details)

All non-2xx responses return `application/problem+json` (RFC 9457, which obsoletes RFC 7807
with a compatible format):

```json
{
  "type": "https://collabhub.dev/problems/validation-error",
  "title": "One or more validation errors occurred.",
  "status": 400,
  "detail": "Channel name must be between 1 and 80 characters.",
  "instance": "/api/v1/channels",
  "traceId": "4bf92f3577b34da6a3ce929d0e0e4736",
  "errors": { "name": ["Required", "Too long"] }   // present only for 400 validation
}
```

- `type` is a stable URI per error class (list below). `traceId` is the W3C trace id.
- Standard classes every service uses: `validation-error` (400), `unauthorized` (401),
  `forbidden` (403), `not-found` (404), `conflict` (409), `rate-limited` (429),
  `internal` (500). Implement once in `collabhub-shared` as a set of FastAPI exception handlers
  (`install_problem_handlers(app)`) mapping domain exceptions → Problem Details.
- **FastAPI returns 422 for request-validation errors by default.** The shared handler MUST
  override `RequestValidationError` to return **400** `validation-error` with the `errors` map
  built from Pydantic's error locations, so all services behave identically.
- Never leak tracebacks or internal messages in `detail` for 5xx (`debug=False` in production).

## 5. Authentication & Authorization

Auth is issued by the **Auth Service** and verified **locally and statelessly** by every
other service. There is no per-request call to the Auth Service to validate a token.

### 5.1 Access tokens (JWT)

- **Algorithm:** RS256. Auth Service publishes its public keys at
  `GET https://auth/.well-known/jwks.json` (root path, not under `/api/v1`). Services verify with
  **PyJWT** (`pyjwt[crypto]`) through a shared verifier in `collabhub-shared` that caches the
  JWKS (refetch on unknown `kid`; hard refresh hourly), exposed to routes as a FastAPI
  dependency (`CurrentUser = Annotated[Principal, Depends(get_current_user)]`).
- **Lifetime:** access token 15 minutes; refresh token 30 days, **rotating** (each refresh
  invalidates the previous refresh token).
- **Claims:**

  | Claim    | Meaning |
  |----------|---------|
  | `iss`    | Issuer — must equal `AUTH__ISSUER` |
  | `aud`    | Audience — must equal `AUTH__AUDIENCE` |
  | `sub`    | User ID (UUID), or the service client ID for service tokens |
  | `name`   | Display name |
  | `email`  | Email |
  | `wsp`    | Active workspace ID |
  | `roles`  | Array of role strings within the active workspace |
  | `jti`    | Token ID (used for revocation) |
  | `iat`/`exp` | Issued / expiry (UTC epoch) |

- **Service tokens:** internal service-to-service calls (e.g. Worker → Asset) use access tokens
  obtained via the OAuth 2.0 `client_credentials` grant from the Auth service, carrying
  `roles: ["service"]` and no `wsp`. Internal endpoints accept only that role.

### 5.2 Revocation (the one stateful part)

Stateless verification can't revoke a token before it expires. To support logout and
forced sign-out, the Auth Service writes revoked `jti`s to a **denylist in Redis Cache (R1)**
with TTL = remaining token lifetime, key `auth:revoked:{jti}`. Services MAY consult the
denylist on each request via R1; if a service cannot reach R1, it fails open (accepts the
signature) and logs a warning — access tokens are short-lived enough that this is acceptable.
(Open decision — see §12.)

### 5.3 Authorization model

- Coarse-grained access is role-based via the `roles` claim (`owner`, `admin`, `member`, `guest`).
- Fine-grained, per-resource permissions (e.g. who can edit a given channel or document)
  are owned by the resource's service in its own tables (see each service's data model).
  Services enforce their own resource permissions; the JWT only establishes identity +
  workspace membership + workspace role.

## 6. Real-Time (Socket.IO) Conventions

SignalR is .NET-specific and has no maintained Python server, so real-time features use
**Socket.IO** via `python-socketio` (`socketio.AsyncServer`, ASGI mode) — the closest
equivalent: rooms (≈ SignalR groups), named events, acknowledgements (≈ hub method return
values), binary payloads, transport fallback, and a Redis manager for multi-pod fan-out.
The SPA uses `socket.io-client`.

- **Mounting:** each real-time service wraps its FastAPI app:
  `socketio.ASGIApp(sio, other_asgi_app=app, socketio_path="hubs/<service>")`, so REST and
  real-time share one process and port. "Hub" in the service docs means this Socket.IO server.
- **Backplane:** `client_manager=socketio.AsyncRedisManager(REDIS__REALTIME_URL, channel="sio:<service>")`
  against **R2**, so any pod can emit to any room. Use a distinct pub/sub `channel` per service.
  Do not put Socket.IO traffic on R1 or R3.
- **Transport & stickiness:** WebSocket preferred, HTTP long-polling fallback (Socket.IO default).
  Long-polling requires **session affinity**: enable cookie-based sticky sessions on the
  ingress for `/hubs/*`. Clients MAY set `transports: ["websocket"]` to skip polling entirely,
  in which case affinity is not needed.
- **Auth:** the client sends the access token in the Socket.IO handshake `auth` payload
  (`{ "token": "<access-token>" }`) — not in the URL, so it never lands in access logs. The
  `connect` handler validates it with the same shared verifier as REST, stores the principal in
  the Socket.IO session (`await sio.save_session(sid, ...)`), and raises
  `ConnectionRefusedError("unauthorized")` on failure. Tokens expire during long connections:
  the server re-checks `exp` on each event and emits `TokenExpired`; the client reconnects with
  a fresh token.
- **Room naming:** `<entity>:<id>` — e.g. `channel:{channelId}`, `doc:{documentId}`,
  `presence:{documentId}`. Every connection also auto-joins `user:{userId}` on connect (for
  delivering to all of one user's sessions). A connection joins entity rooms it is authorized
  for via an explicit join event.
- **Event naming:** client→server events are verbs (`SendMessage`); server→client events are
  past-tense facts (`MessageReceived`). Event names are case-sensitive strings and are
  documented per service. A client→server event that "returns" a value does so via the
  Socket.IO **acknowledgement** (the handler's return value); failures are returned as
  `{ "error": <Problem Details> }` in the ack, never as an unhandled exception.
- **Payloads:** JSON objects with camelCase keys, validated with the same Pydantic models as REST.
  Binary payloads (e.g. Yjs updates) are sent as raw `bytes`, which Socket.IO transmits as binary
  attachments without base64 encoding.

## 7. Asynchronous Jobs (Redis Streams)

Background work flows through **Redis Streams (R3)** (Redis 7+). Producers `XADD`; the Worker
consumes via consumer groups. Producer and consumer helpers live in `collabhub-shared`.

### 7.1 Job envelope

Every stream entry has a single field `data` containing this JSON envelope (Pydantic model
`JobEnvelope[TPayload]` in `collabhub-contracts`):

```json
{
  "jobId": "0192f...-uuid-v7",
  "type": "thumbnail.generate",
  "version": 1,
  "occurredAt": "2026-06-03T10:15:00Z",
  "traceparent": "00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01",
  "payload": { /* type-specific, defined in collabhub-contracts */ }
}
```

- **Stream names:** one stream per domain area — `jobs:index`, `jobs:thumbnail`,
  `jobs:notify`, `jobs:export`, `jobs:retention`. (Producers know which stream; see service docs.)
- **Consumer group:** `worker` on every stream. Worker instances are distinct consumers.
- **Idempotency:** `jobId` is the idempotency key. Handlers MUST be safe to run more than once.
- **Ack / retry:** Worker `XACK`s on success. Unacked entries are reclaimed via `XAUTOCLAIM`
  after a visibility timeout. Stream entries are immutable, so the attempt count is **not**
  kept in the envelope: it is the entry's delivery counter, read from `XPENDING` (extended
  form). Once the delivery count reaches `maxAttempts` (default 5), the entry is copied to
  `jobs:<name>:dead` (with the last error) and acked.
- **Producers never block on the Worker.** Enqueue is fire-and-forget after the primary
  write succeeds. (A failed `XADD` after a committed write loses that job; where that matters,
  use a transactional outbox — see §12.)

## 8. Configuration & Secrets

- All config comes from environment variables (12-factor). No config baked into images.
  Each service declares a `pydantic-settings` `Settings` class; nested settings use `__` as
  the delimiter (`env_nested_delimiter="__"`), so `REDIS__CACHE_URL` maps to
  `settings.redis.cache_url`.
- Non-secret config via Kubernetes ConfigMap; secrets via Sealed Secrets / Vault on-prem,
  Azure Key Vault (CSI driver) on Azure.
- **Common env vars** (every service):

  | Var | Example | Notes |
  |-----|---------|-------|
  | `APP_ENV` | `production` | `development` / `test` / `production` |
  | `POSTGRES__DSN` | `postgresql+asyncpg://user:pass@pg/collabhub_messaging` | Owning DB only |
  | `REDIS__CACHE_URL` | `redis://redis-cache:6379/0` | R1 |
  | `REDIS__REALTIME_URL` | `redis://redis-rt:6379/0` | R2 (only real-time services) |
  | `REDIS__STREAMS_URL` | `redis://redis-streams:6379/0` | R3 |
  | `AUTH__JWKS_URL` | `https://auth/.well-known/jwks.json` | |
  | `AUTH__ISSUER` | `https://auth` | Expected `iss` |
  | `AUTH__AUDIENCE` | `collabhub` | Expected `aud` |
  | `OTEL_EXPORTER_OTLP_ENDPOINT` | `http://otel-collector:4317` | Standard OTel var (OTLP gRPC) |
  | `OTEL_SERVICE_NAME` | `messaging` | Standard OTel var |

- No cloud-specific SDKs where an agnostic alternative exists. Object storage uses the
  S3-compatible API (MinIO on-prem; on Azure an S3-compatible gateway, or an SDK swap behind
  the `ObjectStore` protocol).

## 9. Observability

- **Tracing:** OpenTelemetry Python SDK, OTLP exporter to the collector → Jaeger. Instrument
  FastAPI, httpx, SQLAlchemy/asyncpg and redis via the `opentelemetry-instrumentation-*`
  packages, configured in code in `collabhub-shared` (so setup is identical in tests).
  Propagate W3C `traceparent` across REST, Socket.IO (handshake `auth` payload / event metadata),
  and job envelopes (`traceparent` field).
- **Metrics:** OTel metrics → Prometheus. Standard service metrics + domain counters
  (messages sent, jobs processed, snapshot writes). RED method (Rate, Errors, Duration).
- **Logs:** structured JSON via `structlog` (stdlib `logging` routed through it) → stdout →
  Loki. Always include `traceId`, `userId` (when authenticated), `service`, `env`. No PII in logs
  beyond user IDs.
- **Correlation:** accept and propagate `X-Correlation-Id`; generate one if absent
  (ASGI middleware in `collabhub-shared`).

## 10. Health & Lifecycle

- `GET /health/live` — liveness, no dependency checks. Returns 200 if the process is up.
- `GET /health/ready` — readiness, checks owned dependencies (its Postgres, the Redis
  instances it uses). Returns 503 until healthy. Used by K8s readiness probe.
- Startup/shutdown via the FastAPI `lifespan` context (open/close DB engine, Redis pools,
  JWKS cache, Socket.IO manager).
- Graceful shutdown: Uvicorn handles `SIGTERM` — stop accepting new work, drain in-flight
  requests (`--timeout-graceful-shutdown 25`), then exit. The Worker stops reading new stream
  entries and finishes (or leaves unacked for reclaim) in-flight ones. K8s
  `terminationGracePeriodSeconds: 30`.

## 11. Local Development & Testing

- `docker-compose.yml` at repo root brings up Postgres, the 3 Redis instances, MinIO,
  Elasticsearch, and an OTel collector for local runs.
- `uv sync` installs the whole workspace; each service runs with
  `uv run --package collabhub-<service> uvicorn collabhub_<service>.main:app --reload`.
- Each service ships Alembic migrations; `uv run alembic upgrade head` per service against
  its own database (or schema-per-service on one local Postgres for convenience).
- Test layers (pytest + `pytest-asyncio`): unit (domain logic), integration
  (`testcontainers` for Postgres/Redis/MinIO/ES; FastAPI via `httpx.AsyncClient` +
  `ASGITransport`), contract (verify the Pydantic models in `collabhub-contracts` and each
  service's OpenAPI schema against consumers).

## 12. Open Decisions (confirm before/while building)

1. **Denylist consultation** — do all services check the Redis denylist on every request
   (stronger revocation, R1 dependency) or rely purely on short token lifetime (simpler,
   weaker)? Default assumed: check-with-fail-open (§5.2).
2. **Workspace/tenancy** — `wsp` claim assumes a single active workspace per token. Confirm
   whether users belong to multiple workspaces and how switching works.
3. **ID generation** — UUID v7 assumed over bigint/ULID. Confirm.
4. **Schema-per-service vs database-per-service** in production. Doc assumes logically
   separate databases; on-prem you may co-locate.
5. **Real-time transport** — Socket.IO (assumed, §6) vs. plain WebSockets (FastAPI/Starlette)
   with a hand-written Redis pub/sub fan-out. Socket.IO gives rooms, acks, reconnection and
   fallback out of the box; plain WebSockets avoid the extra protocol layer and sticky sessions.
6. **Job enqueue durability** — fire-and-forget `XADD` after commit (assumed, §7) vs. a
   transactional outbox per producing service.
